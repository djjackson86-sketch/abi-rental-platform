{# The browser half of the public portal's double-submit guard (client portal changes). The registration form writes a customer, so a second tap while the first request is still in the post must not send a second one. This disables the submit button the moment a valid form is submitted and relabels it, so the button both cannot be pressed twice and says what is happening instead of looking dead. The server holds the real guard (a per-submission claim key that the form also carries), so this is a courtesy, not the boundary. Two browser-warts it defends against: * a disabled submit control is dropped from the posted form data, so a **named** button would silently lose its value - the pressed button's name/value is mirrored into a hidden field BEFORE disabling it; * Safari restores a page from the back/forward cache exactly as it was left, with the button still disabled and the panel still busy - on pageshow with event.persisted the panel is reset (aria-busy cleared, button re-enabled and relabelled) so the customer can submit again; * Chrome likewise restores the previous form state onto the response document, so a validation re-render can arrive with the button already stuck on "Sending..." - every load therefore resets, not just a persisted pageshow. Kept free of square brackets: a walk test asserts no customer-facing page carries a bracketed placeholder token. Included by the portal form. #}
